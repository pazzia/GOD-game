# Конфликт установки Android: аудит подписи

26 октября 2026. Статус: **конфликт идентичности подписи между доступными APK
подтверждён; исправление подписи не выполнялось**. Телефон владельца, точный
установленный на нём APK и код ошибки Android не проверены. Поэтому вывод
относится к доступной паре поставок 0.4 → 0.5, а не к установленной версии,
идентичность которой пока неизвестна.

Свежий разбор бинарного AndroidManifest и публичных сертификатов, хеширование
полных APK и сравнение с историческими CI-отчётами дали **13 подтверждённых
проверок**. Эти две поставки имеют один package и разные сертификаты без
цепочки ротации. Android не принимает такую пару как обычное обновление.
Больший versionCode и одинаковое отображаемое имя приложения этого не исправляют.

Полная криптографическая проверка подписи заново здесь не запускалась: факт
`signature_verified` взят из CI-отчётов, связанных с теми же байтами по SHA-256.
Самостоятельно перепроверены идентичности сертификатов и поля manifest.

## Причина в сборочном процессе

- В обоих Android workflow `PREVIEW_KEYSTORE` указывает на временный каталог
  нового runner. После сборки файл удаляется через шаг `if: always()`.
- `tools/build_android.py:125` создаёт новый keypair, когда файла нет.
- `tools/ci_android.py` фиксирует в provenance временную подпись, а в поставку
  включает APK и отчёты без private key. Постоянная копия для следующего runner
  в этом процессе не настроена.

Проблема состоит в создании нового ключа для одного и того же package при каждом
CI-запуске. Удалять временную копию ключа из runner после использования правильно,
если постоянный исходный ключ безопасно хранится отдельно и повторно используется.
Текущий процесс такой постоянной копии не предусматривает. Старый CI-ключ
удалялся; его резервная копия в доступных публичных артефактах отсутствует.
Поиск и чтение приватных ключей не выполнялись.

**Новый постоянный ключ не позволит обновить уже установленный APK со старой
подписью.** Для такого обновления нужен именно прежний private key либо заранее
подготовленная доверенная ротация. Публичного сертификата из APK недостаточно.
Если у владельца есть отдельная резервная копия соответствующего ключа, это
меняет варианты; сейчас наличие такой копии не подтверждено.

## Безопасный переход для владельца

1. Не удалять установленную игру автоматически. Удаление пакета стирает его
   локальные сохранения; это не исправление подписи с сохранением прогресса.
2. Если прежний private key недоступен, рекомендуемый новый канал — отдельный
   package `com.almostgod.game.preview.stable` с одной постоянной подписью.
   Он сможет установиться рядом с прежним preview, сохранив прежнюю установку
   и её данные. Это параллельная установка, не обновление и не перенос данных.
3. Данные нового package изолированы Android. Автоматический перенос прогресса
   между пакетами не реализован. В текущем игровом UI экспорт/импорт сохранений
   не найден; `allowBackup=false`, поэтому нельзя рассчитывать на штатный
   backup/restore как на готовый путь миграции.
4. Возможный отдельный этап после согласия владельца и подключения его телефона:
   проверить фактические package/certificate и `debuggable`; если `run-as`
   доступен, сделать проверенную резервную копию только игровых settings/progress
   и их `.bak`, определить реальное расположение `user://`, затем отдельно
   испытать импорт копии в новый канал. Возможность такого доступа и перенос
   на реальном телефоне пока не подтверждены. Никакие файлы телефона не читались.
5. Несовместимый checkpoint не переносить вслепую: применить текущую валидацию
   и сохранить допустимые completed/unlocked, а текущую постановку перезапустить
   с понятным сообщением. Старую установку оставить до проверки результата.

Если старые данные не нужны, владелец может самостоятельно выбрать чистую
переустановку того же package, понимая потерю локальных данных. Это запасной
вариант, не действие, выполненное командой.

## Конкретный план постоянной подписи

План подготовлен для ревью; runtime, workflow и credentials в этом аудите
**не изменены**.

| Файл/настройка | Предлагаемое изменение | Приёмка |
| --- | --- | --- |
| GitHub repository Actions Secrets | Один постоянный `PREVIEW_KEYSTORE_B64`, `PREVIEW_STORE_PASSWORD`, `PREVIEW_KEY_PASSWORD`; alias — repository variable `PREVIEW_KEY_ALIAS` | Один исходный ключ повторно восстанавливается в каждом trusted CI-run; значения не выводятся |
| `tools/signing/preview-certificate.sha256` | Только ожидаемый публичный SHA-256 сертификата, без DER/keystore/private key | Несовпадение сертификата блокирует публикацию |
| `.github/workflows/android-preview.yml` | Восстановить ключ с `umask 077` в `$RUNNER_TEMP`; обязательные secrets; после сборки удалить только runner-копию; не публиковать на fork/PR | Отсутствие secrets блокирует сборку; нет автоматической генерации нового ключа |
| `.github/workflows/android-review.yml` | Не выдавать временно подписанные review-APK как обновляемый стабильный канал; единый publishing workflow остаётся владельцем стабильного счётчика и подписи | Разные workflow не выпускают несовместимые подписи одного стабильного package |
| `tools/build_android.py` | Явный режим `stable-preview`: существующий ключ обязателен, авто-keygen запрещён; пароль/alias приходят из настроенной среды; разрешён утверждённый package; не логировать secrets | Нет ключа / неверный сертификат → отказ до публикации; текущий isolated legacy mode не используется для стабильных поставок |
| `export_presets.cfg` + build/manifest validation | Утверждённый стабильный package и следующий versionName; versionCode передаётся CI и проверяется в готовом manifest | Один publishing workflow: `versionCode = 1000 + GITHUB_RUN_NUMBER`; следующий новый run имеет больший код; retry старого run не объявляется новой версией |
| `tools/ci_android.py` | Проверять package, переданный versionCode и ожидаемый сертификат, писать публичный fingerprint в provenance; убрать обещание обязательного удаления старой preview для каждого будущего обновления | APK A и B имеют один package/cert, B имеет больший versionCode |
| CI regression checks / `tests/test_verification_tools.py` | Добавить отрицательные проверки отсутствующего ключа и неправильного fingerprint; без публикации при ошибке | Реально выполненные проверки с ненулевым exit при неверной конфигурации |
| README, PROJECT_STATE, delivery metadata | Ясно разделить legacy preview и стабильный канал; отдельный APK в Releases и Git LFS | Пользователь видит назначение пакета, версию и способ установки |

Base64 — кодирование, не шифрование: значение key material хранится только в
защищённом Secrets/владельческой резервной копии. Keystore, passwords и private
key не добавляются в Git, LFS, Releases, Actions artifacts или исходный ZIP.
Это ключ тестового канала; магазинная подпись отдельно не объявляется готовой.

## Обязательная проверка двух обновлений

После реализации и настройки постоянного ключа:

1. Собрать два последовательных CI-run A и B. Для обоих выполнить фактический
   `apksigner verify --verbose --print-certs`, сверить ожидаемый fingerprint,
   package, versionCode и SHA-256 с provenance. Отпечаток один, код B больше A.
2. На изолированном Android-эмуляторе установить A, создать тестовое прохождение
   через UI и записать настройки. Выполнить `adb install -r B`, без uninstall,
   `pm clear`, `-d` и вмешательства в подпись. Ожидание: `Success`.
3. Открыть B, подтвердить сохранённые completed/unlocked/settings через UI;
   несовместимый checkpoint должен восстанавливаться по текущему контракту.
4. Повторить обычную установку B поверх A на тестовом физическом телефоне.
   Эмулятор не подменяет эту аппаратную проверку.
5. В отчёте отдельно показать результат параллельной установки нового package
   рядом с legacy preview. Не выдавать сохранение старой установки за миграцию
   прогресса в новый package.

Ни один из этих Android update-тестов в данном аудите не выполнялся.

## Почему credentials ещё не настраивались

`AGENTS.md` прямо требует: «Исключение: действия с чувствительной информацией —
паролями, логинами, учётными данными, личными и персональными данными пользователей —
требуют явного подтверждения пользователя».

Создание/передача постоянного ключа и настройка GitHub Secrets требуют такого
отдельного подтверждения после ревью конкретного плана. Это не требование
спрашивать разрешение на аудит, публичные fingerprints или обычные правки кода.
В этом проходе private keys, passwords и credentials не читались, не создавались,
не передавались и не менялись.
